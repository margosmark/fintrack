# 52 — Android native authentication and read-only API contract

**Status: evidence-backed design recommendation; no Android auth implementation or backend change authorized by this document.** Checked against repository source on **2026-10-29** (branch snapshot `origin/main`, commit `4f33e97a9e83c36873a466b2c49a2e108d7a900e`). Android app implementation is approved by [docs/51](51-android-home-screen-widgets.md); this document resolves the current auth boundary and records any change that must be separately gated. It does not authorize production access or testing.

## Decision summary

| Question | Verified answer / recommendation |
| --- | --- |
| What does the SPA use? | A 15-minute access JWT held in JavaScript memory and a 30-day opaque rotating refresh credential delivered only in an HttpOnly cookie. The exact cookie is `refresh_token`, path `/api/v1/auth`, `HttpOnly`, `Secure` according to `COOKIE_SECURE` (default `true`), `SameSite=Strict`, `Max-Age=refresh_token_days × 86400` (default 30 days). The cookie has no explicit `Domain` or `Expires` set in this code. [`frontend/src/api/client.ts:18-21`](../frontend/src/api/client.ts#L18), [`backend/app/api/auth.py:69-70,83-102`](../backend/app/api/auth.py#L83), [`backend/app/core/config.py:19-20,64`](../backend/app/core/config.py#L19) |
| Can the existing refresh endpoint accept a native token in JSON or an Authorization header? | **No.** It reads only the named cookie; body-carried refresh tokens are expressly rejected by design. [`backend/app/api/auth.py:133-151,366-387`](../backend/app/api/auth.py#L133) |
| Lowest-change native path? | Use a dedicated app HTTP client with a persistent, app-scoped cookie jar for the existing cookie flow; keep access JWT only in process memory, rotate serially, and clear the jar/cache on logout and identity transition. This is a bearer cookie stored by the app—not a browser cookie magically protected by `HttpOnly`. No backend protocol change is needed. |
| When would the backend need to change? | Any native refresh-token JSON/header protocol, device-bound/rotatable native credential type, per-device session listing/revocation, or distinct native login/session policy. These are not existing contracts and require an explicitly approved backend/security change before use. |

## 1. Current authentication surface

API routes are mounted below `/api/v1`; `auth.py` declares the `/auth` router. [`backend/app/main.py:247-250`](../backend/app/main.py#L247)

### Credential issuance and response shape

- `POST /api/v1/auth/login`: verifies the password; unknown-user and bad-password responses are both 401. If TOTP is enabled (except demo), it returns a short-lived TOTP challenge **without a session or refresh cookie**. Otherwise it issues the pair and sets the refresh cookie. [`backend/app/api/auth.py:285-314`](../backend/app/api/auth.py#L285)
- `POST /api/v1/auth/demo`: when enabled, ensures the shared demo user, issues a pair and sets the same cookie. The response does not create a special read-only credential. [`backend/app/api/auth.py:317-331`](../backend/app/api/auth.py#L317)
- `_issue_pair`: creates a refresh token, stores only its SHA-256 hash with user and expiry, and returns an access JWT plus user. `TokenResponse.refresh_token` is excluded from JSON; the raw refresh value is used only to set the cookie. [`backend/app/api/auth.py:169-185`](../backend/app/api/auth.py#L169), [`backend/app/schemas/auth.py:29-39`](../backend/app/schemas/auth.py#L29), [`backend/app/models/refresh_tokens.py:11-19`](../backend/app/models/refresh_tokens.py#L11)
- Access JWTs carry `type=access`, user subject, issue time and expiry; expiry is configured as 15 minutes by default. Refresh tokens are opaque 32-byte random values, hashed with SHA-256 for storage. [`backend/app/core/security.py:29-66`](../backend/app/core/security.py#L29), [`backend/app/core/config.py:19-20`](../backend/app/core/config.py#L19)
- Additional successful sign-in paths also call the same pair/cookie helpers: TOTP/recovery and passkey verification (`backend/app/api/auth_second_factor.py`) and OIDC confirmation (`backend/app/api/auth_oidc.py`). Password login itself can return a TOTP challenge, so a native password flow must not treat every HTTP 200 as an authenticated session. [`backend/app/api/auth.py:301-314`](../backend/app/api/auth.py#L301), [`backend/app/api/auth_second_factor.py:291-293,321-323,589-591`](../backend/app/api/auth_second_factor.py#L291), [`backend/app/api/auth_oidc.py:259-262`](../backend/app/api/auth_oidc.py#L259)

### Refresh, rotation and logout

- `POST /api/v1/auth/refresh` takes **no request model/body** and reads only the `refresh_token` cookie. It atomically claims/consumes the current token, rejects missing/expired/revoked tokens, creates a successor pair, and sends the replacement refresh cookie. Concurrent use of one token has one winner; detected reuse of a non-expired spent token revokes every still-live refresh token for that user (chain-wide), not just the raced device. [`backend/app/api/auth.py:194-232,366-431`](../backend/app/api/auth.py#L194)
- An expired token is not itself treated as evidence of compromise and does not cascade-revoke other sessions. On invalid refresh, server clears the cookie. [`backend/app/api/auth.py:390-417`](../backend/app/api/auth.py#L390)
- `POST /api/v1/auth/logout` is also cookie-only. It revokes the presented refresh-token row, commits, clears the cookie and returns 204. It does **not** revoke all of the user’s other refresh-token rows. [`backend/app/api/auth.py:434-458`](../backend/app/api/auth.py#L434)
- **Access-token logout caveat:** the access JWT is stateless and is checked for signature/type/expiry; these paths show no access-token blacklist/revocation lookup. Therefore a copied access JWT can remain usable until its expiry after refresh-token logout, up to the configured access-token lifetime. [`backend/app/core/security.py:29-53`](../backend/app/core/security.py#L29), [`backend/app/api/deps.py:137-159,182-189`](../backend/app/api/deps.py#L137)

### Exact cookie attributes

Set: name `refresh_token`; `HttpOnly=true`; `Secure=settings.cookie_secure` (default `true`; runtime configuration may override); `SameSite=Strict`; `Max-Age=settings.refresh_token_days * 86400` (default 30 days); `Path=/api/v1/auth`. No `Domain` parameter is set, so it is host-only by ordinary cookie semantics; no explicit `Expires` is set. Clear uses the same name, path, HttpOnly, Secure setting and SameSite, with deletion semantics. [`backend/app/api/auth.py:69-70,83-115`](../backend/app/api/auth.py#L69), [`backend/app/core/config.py:19-20,64`](../backend/app/core/config.py#L19)

`HttpOnly` prevents browser JavaScript from reading the cookie; it does **not** make a cookie stored by a native HTTP client inaccessible to that app’s process, protect a compromised/rooted device, or bind the credential cryptographically to an installation. Those Android-specific properties are not established by repository code.

### Authorization and tenant/read-only guards

- Ordinary authenticated API routes use `get_current_user`, which accepts a Bearer access JWT, resolves its user, then applies the demo write guard before the handler. [`backend/app/api/deps.py:137-159,162-200`](../backend/app/api/deps.py#L137)
- `owned_or_404` returns a record only when `user_id` matches the authenticated user; otherwise it returns a generic 404. Domain list/query handlers also filter on the authenticated user. [`backend/app/api/deps.py:239-244`](../backend/app/api/deps.py#L239)
- Mutating methods for the demo user are rejected with 403 `demo_account_restricted`, except for narrowly listed recovery/credential/pure-computation routes. GET/HEAD/OPTIONS reads remain available. [`backend/app/api/deps.py:40-40,86-120`](../backend/app/api/deps.py#L40)
- The display mask does not alter API payloads, encrypt data or grant/restrict server authorization. It is a render-time transformation stored per browser tab in `sessionStorage`. A native client must implement and test its own presentation/privacy policy; it must never claim the mask protects cached data or the network. [`frontend/src/lib/mask.ts:1-22`](../frontend/src/lib/mask.ts#L1)

## 2. Native gap and choices

The SPA can rely on its browser’s cookie handling for its same-origin `fetch`; it keeps the access token in memory and the refresh token out of JavaScript. [`frontend/src/api/client.ts:18-21,266-279,314-365`](../frontend/src/api/client.ts#L18) A native HTTP stack is not that browser context: it needs an explicit cookie store and must send the cookie to `/auth/refresh` and `/auth/logout`. Current server endpoints do not accept a refresh token in a body or bearer header. [`backend/app/api/auth.py:133-151,381-385,441-445`](../backend/app/api/auth.py#L133)

| Option | Session-theft exposure | Logout / revocation today | Identity change and cache | Does it preserve the current guarantee? / backend change |
| --- | --- | --- | --- | --- |
| **A. App-scoped cookie jar (recommended for v1)** | The app HTTP client can use the existing HttpOnly `Set-Cookie` flow. `HttpOnly` is not a protection from the native app itself: the cookie jar/process can use it, and a copied cookie is a bearer refresh credential. Persisting it unencrypted or including it in backups/logs raises theft risk. Protect persisted jar material using an Android Keystore-backed design; do not call the cookie “device-bound.” | Existing `/auth/logout` revokes that cookie’s refresh row and clears it. Rotation and reuse detection remain the server’s current behavior. Logout leaves other device sessions alone; any copied access JWT can survive until expiry. | On explicit logout, revoke first where possible, clear cookie jar/access token/local query and widget caches, then permit a different identity. If switching users, do not silently overwrite a still-live refresh cookie and retain any prior user content. `AuthContext` removes the SPA query cache and reinitializes mask on user-ID changes; native must reproduce the privacy outcome for every local store. [`frontend/src/auth/AuthContext.tsx:136-151`](../frontend/src/auth/AuthContext.tsx#L136) | Keeps cookie-only refresh, short-lived in-memory access token, server rotation/revocation and response semantics. No backend change. Cookie is app-scoped by client configuration, **not** a new cryptographic guarantee; the SPA’s browser `HttpOnly` boundary does not transfer to native code. |
| **B. Native refresh token in Keystore-protected storage** | Encryption at rest can reduce offline extraction of a copied preferences/database file, but an unlocked/compromised running app can still use a decrypted bearer token. Keystore protects keys/operations; it does not by itself bind this server token to a device or stop live-process theft. | Current refresh/logout handlers will not accept a raw token sent in JSON/header. A cookie could be encrypted locally then restored into a CookieJar, but that is still Option A on the wire; sending it as an Authorization token is not supported. | Keystore-backed token storage must be deleted at logout/account change and all tenant-derived caches purged before new-user UI appears. Device/app uninstall, key invalidation, backup/restore and offline logout behavior need a designed/tested policy; no such Android implementation exists in this repo. | **Cannot be implemented as a different wire protocol today.** A native-only token endpoint/header/body, device/session identifier, independent rotation family or explicit revocation endpoint requires a backend/security design and approval. Do not bypass the cookie-only parser. |
| **C. Non-persistent in-memory cookie jar** | Least durable local credential exposure; process death loses the refresh session. A live compromised process can still use it. | Same server logout/rotation while process is alive; if app dies without logout, the server-side refresh row remains live until expiry/revocation/reuse detection. | Identity data and app memory must be purged on switch; after process death user signs in again. This avoids persistent refresh-token storage but gives no session restoration. | Existing backend flow can work, with no change. Useful as a stricter fallback if product accepts sign-in on each process restart; it is not persistent login. |

### Recommendation and gates

1. **Use Option A for the Android app’s first authenticated read-only client**, behind a dedicated API client/CookieJar, unless the Android security review rejects persistent app-private cookie storage. Keep the access JWT in memory only. Serialize refresh requests: the backend rotates one token and a concurrent loser can trigger chain-wide revocation. The SPA already uses single-flight refresh for precisely this reason. [`frontend/src/api/client.ts:76-110,314-330`](../frontend/src/api/client.ts#L76)
2. Store the persistent cookie jar only in app-private storage with a reviewed Keystore-backed protection/backup policy; never expose cookie values to UI, logs, analytics, clipboard, deep links, widget state, or ordinary preferences. The exact Android persistence/encryption library and guarantees are **unverified/not selected** here; verify against current Android guidance during implementation/security review.
3. On logout or account change, stop in-flight requests, attempt server logout with the current jar, clear the jar and access JWT, then synchronously purge all account-derived query/local/widget data before rendering a different identity. If offline, clear local credentials/data anyway and disclose that server revocation cannot be confirmed until connectivity returns; this offline behavior is a design requirement, not an existing server guarantee.
4. Keep Android v1 read-only even though an ordinary account’s bearer token could call mutation routes. UI hiding is not authorization. The server’s demo-only read-only guard does not make regular accounts read-only. A future client-wide read-only token/scope is a separate backend authorization project and must be gated.
5. **Do not add a native refresh-token header/body** as a “storage detail.” The current cookie-only rule was specifically adopted to keep long-lived credentials out of scripts/logs/proxy captures. Any new native credential protocol would change this security boundary, token acceptance rules, revocation and likely threat model; require explicit backend, security and QA approval before implementation.
6. If future widget/background operation requires independently revocable credentials, proceed to a separately approved **native session contract**: per-install/session identity; short-lived access; rotating opaque refresh credential stored with Keystore-backed protection; replay/reuse policy; per-session logout/revocation and account-wide revoke semantics; expiry and offline behavior; identity-transition cache purge. Every element in this sentence is a proposal, **not a verified current feature**.

### Account detail: holdings section, ledger, and value formatting

The account-detail screen (`account/{accountId}`) composes three **independent** sections — each with its own presenter, state and retry, so one failing fetch never collapses the others (docs/53 AC1.3):

| Section | Fetch | When it is composed | Empty / negative state |
| --- | --- | --- | --- |
| **Details** | `GET /accounts/{account_id}` | always | its own `SectionState` |
| **Holdings** | `GET /portfolio/positions?account_id={account_id}` | only after that account row is `Ready` **and** its `type` is an investment type | `SectionState.*`; a successful empty page → `NoData` with heading `No holdings yet` |
| **Ledger** | `GET /accounts/ledger?account_id={account_id}` | always | its own `SectionState`; empty → `NoData` (`No entries yet`) |

**Gating.** `INVESTMENT_ACCOUNT_TYPES` = `{brokerage_non_registered, rrsp, tfsa, fhsa, resp, lira, rdsp}` — the client mirror of `backend/app/models/accounts.py::INVESTMENT_ACCOUNT_TYPES`, i.e. exactly the types the server accepts trades on (`422 account_not_investment` otherwise). The positions route can queue market-hours price/fundamentals refresh work (see the freshness bullet below), so a cash account never asks for rows the server cannot return: no account-scoped `GET /portfolio/positions` is issued at all, and no holdings section is composed. While Details is still `Loading` (or has failed) there is no holdings section to mis-state.

**Holdings row.** Every figure is the response's own string; nothing is summed, converted or re-priced client-side (docs/53 AC1.1).

- left: `symbol`, then `qty <quantity>` — a quantity is a unit count, not a monetary value, so it renders unmasked (same treatment as the holding-detail screen);
- right: `market_value_native` in `listing_currency`, then `≈ <market_value_cad> (portfolio)`, then `Unrealized gain <unrealized_gain_cad> (portfolio)` when present;
- `market_value_native == null` renders `No market value` — never `0` (docs/53 AC1.3);
- beneath the row: the shared freshness/provenance chips (`price`, `price_source`, `price_date`, `price_age_days`, `price_stale`) plus the server's own staleness banner when `price_stale && price_date` (`Showing saved prices`), so price age is never presented as live;
- the request carries `account_id=<route id>` and only that response is rendered — tenant/ownership scoping stays server-side (`owned_or_404`).

**Account-detail value formatting.** `ui/screens/AccountValueFormat.kt` is the render seam for money/price/quantity strings on this screen (grouping and a sensible precision, so a balance reads `1,234,567.90` instead of `1234567.895`):

| Function | Precision | Example |
| --- | --- | --- |
| `amount` | grouped, exactly 2 decimals | `1234.5678` → `1,234.57` |
| `price` | grouped, 2–4 decimals | `0.05123456` → `0.0512` |
| `quantity` | grouped, 0–6 decimals, trailing zeros trimmed | `000010.0000` → `10` |

Rules: parse-and-re-render only (HALF_UP, the repo's money convention) — **no arithmetic**, so a mutated server string still shows up as that mutation; a non-zero value that would round to zero at the target precision is returned **unformatted** rather than displayed as `0.00`; unparsable input passes through verbatim; grouping follows `Locale.getDefault()` (tests pin `Locale.US` and `Locale.GERMANY`). Formatting happens **after** the wire decode — `finance/FinanceModels.kt` stays verbatim — and **before** masking, so `MaskedText` masks the formatted string (bullets are fixed-length, so grouping reveals nothing). Home/glance keeps its own formatter (`HomeNumberFormat`); the two seams are intentionally separate for now (an integrator may fold them into one later).

**Stable tags:** `account_detail_holdings` wraps the holdings section; the shared `SectionTags.*` state tags live inside it.

### Freshness and provenance limits to preserve

- A market `price_date` and `price_age_days` describe the date/age of the cached close, **not** the time the server fetched it. `price_fetched_at` is separate evidence and may be null; do not substitute row creation/update time or client request time. Manual prices intentionally have no provider fetch timestamp. [`backend/app/models/prices.py:29-44`](../backend/app/models/prices.py#L29), [`backend/app/schemas/prices.py:25-42`](../backend/app/schemas/prices.py#L25), [`backend/app/api/prices.py:140-161`](../backend/app/api/prices.py#L140)
- `last_sync_at` is nullable account provider-sync status, not a universal “data checked at” timestamp. FX `as_of` is a rate date, not a request timestamp. The source routes do **not** expose a common `server_checked_at` for the whole glance payload. If UI needs “last checked,” show a client-observed successful response time as client observation (with timezone/wording clear), or request a separately designed server field; do not represent it as server-supplied. [`backend/app/schemas/accounts.py:64-67`](../backend/app/schemas/accounts.py#L64), [`backend/app/schemas/fx.py:62-91`](../backend/app/schemas/fx.py#L62)
- `GET /portfolio/positions` can queue automatic price/fundamentals refresh work during market hours; `GET /securities/{security_id}/overview` attempts a provider price refresh during the request and should not be treated as an inert cache-only read. Prefer the positions route for the compact holding glance; any provider refresh behavior must be disclosed and rechecked for native use. [`backend/app/api/portfolio.py:199-221`](../backend/app/api/portfolio.py#L199), [`backend/app/api/securities.py:312-330`](../backend/app/api/securities.py#L312)
- The price stream is an existing authenticated SSE read, but it accepts an access token as a query parameter for EventSource compatibility and emits cached data; it polls the database every five seconds, does not fetch providers, and is not a native background/widget delivery guarantee. Do not put refresh tokens in a URL or claim the native app is real-time. [`backend/app/api/deps.py:203-214`](../backend/app/api/deps.py#L203), [`backend/app/api/_price_stream.py:30-38,80-120`](../backend/app/api/_price_stream.py#L30)
- Presentation masking is client-side: payload amounts still travel over authenticated API and remain unencrypted data in process memory. A value-bearing widget/local snapshot has a separate OS-surface, storage, lifecycle and identity-purge policy; do not inherit a claim of “encrypted” or “masked” from the SPA. [`frontend/src/lib/mask.ts:1-22`](../frontend/src/lib/mask.ts#L1)

## 4. Non-negotiables for the Android client

1. **Server-owned truth:** render server-returned account, position, transaction, price, currency, provenance and freshness values. Do not reconstruct balances, portfolio totals, FX conversions, prices, gains, transactions or freshness client-side. Server schemas may supply null/unknown; preserve it as unavailable/unknown rather than zero. [`backend/app/api/portfolio.py:150-160,188-196`](../backend/app/api/portfolio.py#L150), [`backend/app/schemas/accounts.py:48-61,110-129`](../backend/app/schemas/accounts.py#L48)
2. **Read-only means no mutation calls in v1:** no POST/PUT/PATCH/DELETE domain routes, no optimistic writes, no transaction edits, no price/FX changes, no demo reset. Client navigation is not a security boundary. Demo is read-only server-side, but this client scope remains read-only for every identity. [`backend/app/api/deps.py:99-120`](../backend/app/api/deps.py#L99)
3. **Tenant isolation:** every request uses the current authenticated identity; never trust IDs alone. Clear auth state and every private local/query/widget cache before displaying a different identity. Server ownership scopes/404s remain authoritative. [`backend/app/api/deps.py:182-200,239-244`](../backend/app/api/deps.py#L182), [`backend/app/api/accounts.py:318-348`](../backend/app/api/accounts.py#L318), [`backend/app/api/transactions.py:325-400`](../backend/app/api/transactions.py#L325)
