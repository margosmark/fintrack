Configuration (MCP)

The endpoints, payload shapes, and policies behind agent access — the reference page for humans and their agents.

  1. Three endpoints, one secret

    You mint and revoke tokens against /api/v1/auth/mcp-tokens with your normal login. The MCP server itself validates the bearer token at /api/v1/auth/validate-mcp-token, and it posts each receipt to /api/v1/auth/internal-mcp-audit — those two are internal, denied at the reverse proxy, and reachable only from the compose network. You read receipts at /api/v1/mcp-audit. Nothing about this needs configuration beyond the three variables the MCP container runs on.

  2. Full or read-only

    The policy is set when the token is created and cannot be changed afterwards — mint a new one instead. A full token sees all 105 tools. The demo tenant never gets one: its mints are forced to read_only (an omitted policy resolves to read_only, an explicit full is refused with 422 demo_mcp_read_only), so a demo session always lists the 52. A read-only token sees the 52 that only read, and any attempt to call a mutating tool is answered with 403 and code mcp_read_only at the MCP layer, before a request is made. Existing tokens keep the policy they were created with, so nothing changes for a deployment that never asked for read-only.

  3. The three environment variables

    FIN_TRACKER_URL is where the MCP server finds the API (http://<host>:8000 — the API's address as the MCP container reaches it, never a public URL), MCP_INTERNAL_SECRET is the shared secret it uses to ask for a per-user session and to post receipts, and MCP_UPLOAD_DIR is the directory file imports are allowed to read — paths outside it are refused. The container holds no database credentials and no login secret on purpose: it only ever speaks HTTP to the API.

  4. What a receipt code means

    Codes are derived, never guessed: a refusal decided at the MCP layer is 403, a status the API itself returned is passed through as-is, a tool error that came back as the app's structured error is 400, and an unexpected failure is 500. Everything else is 200. Receipts are best effort by design — if the API is unreachable when a call finishes, the tool result is still returned and the gap is logged rather than blocking your work.

  5. Counts worth knowing

    105 tools in total: 52 read and 53 write, where the read set is every GET plus seven POSTs that only compute or manage a session (logging in, refreshing, logging out, the demo switch, running a projection, testing the model connection, and suggesting an import profile). The split is derived from the tool code itself, so a tool added later is classified when it lands rather than when someone remembers to update a list.
