Migrate from YNAB

Export your budget, review the whole mapping before anything is written, then import — refused rows are listed, never dropped.

  1. Export from YNAB

    Whole budget (recommended): in YNAB open Settings → Developer and create a personal access token, then save the response of GET https://api.ynab.com/v1/plans/last-used (Authorization: Bearer your-token) to a file ending in .json — that one call is YNAB's own full-plan export, carrying accounts, category groups, categories, payees, and every transaction. One account at a time: use the account's Export option to download its register as CSV — no token needed, but the file has no category tree and no targets.

  2. Preview the whole plan first

    Imports → Import a YNAB budget → choose the file → Preview. Nothing is written: you see every account that will be created or matched by name, each category group becoming a top-level category with the group name attached as a tag, each target as a budget or goal, and every transaction with its date, amount, memo, and cleared state — plus each row the import refuses, carrying its row number and the reason.

  3. Import, then commit batch by batch

    Press Import and each account's transactions land in their own review batch, exactly like a bank statement upload: balances, budgets, and reports do not move until you commit a batch. Transfers arrive as linked pairs, and YNAB's cleared / reconciled flags stay on every row.

  4. Safe to run twice

    Accounts, categories, and tags match existing ones by name, and transactions dedup against staged and committed rows alike — importing the same file again stages nothing new, and the preview tells you so before you try.

  5. Check the two tables below

    What maps cleanly, and what does not come across — read them before you cancel anything on the other side.

What maps cleanly

In YNABHere
Accounts — chequing, savings, credit cards, loansMatched by name when you already have one, otherwise created with the closest account type. Taxability is derived the same way as a hand-made account.
Category groupsBecome top-level categories, and the group name is attached as a tag on that group's transactions.
CategoriesBecome child categories under their group, so the two-level tree survives.
Targets — monthly fundingBecome a monthly budget on that category. An existing budget amount is never overwritten.
Targets — target balance, with or without a dateBecome a goal with the amount and date.
TransactionsEvery row with its date, amount (YNAB's milliunits converted to dollars and cents), payee, and memo folded into the description.
Cleared and reconciled flagsKept on each row (uncleared / cleared / reconciled).
Transfers between your accountsBoth sides imported and linked as one transfer pair.

What does not come across

In YNABWhat happens here
Split detailThe parent total imports as one row; the split lines are reported as a warning instead of being imported.
Scheduled transactionsSkipped — reported once as a note on the preview.
Targets other than monthly funding or target balance (needed-for-spending, debt)Refused with a reason in the preview, never silently skipped.
Reconciliation progress and account running balancesNot imported. The cleared / reconciled flag on each individual row still comes across.
Group funding and underfunded amountsNot imported — budgets and goals are yardsticks here, and nothing is moved or auto-spent.
Payee-to-category memories (YNAB's learned rules)Not imported; payee learning starts fresh from the suggestions you confirm.
Closed accountsImported as open accounts — the preview notes it.
Deleted accounts, categories, and transactionsSkipped and reported in the preview notes.
Account opening balances or a partial exportBalances rebuild from the transactions in the file, so a trimmed export shows different balances than YNAB did.
A budget on a tenant with encryption requiredThe import stops with a clear error before writing anything — the server cannot create your encrypted rows. Manual entry with client-side encryption still works.
