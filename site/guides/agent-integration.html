Drive it from your AI agent

Connect Claude, Cursor, or your own script to your own fin_tracker — a scoped token, a read-only mode, and a receipt for every call.

  1. Mint a token in one call

    Sign in the way you normally would, then POST to /api/v1/auth/mcp-tokens with a name and a policy — for example {"name":"laptop-agent","policy":"read_only"}. The response carries an opaque 64-character token that is shown exactly once and stored only as a hash; it expires 90 days after you create it. Omit policy and you get full — the behaviour every token had before policies existed. The demo tenant runs the same recipe with one rule: its tokens are always read-only, so an omitted policy gives you read_only and an explicit "full" is refused with 422 code demo_mcp_read_only instead of being quietly downgraded. Revoke any token at any time with DELETE /api/v1/auth/mcp-tokens/{id} — the demo tenant can revoke its own tokens too.

  2. Point your client at /mcp/mcp

    The Model Context Protocol endpoint lives on the same host as the app, one path deeper: https://your-server/mcp/mcp. Add it to your client as a remote server with your token as a bearer header — {"mcpServers":{"fin_tracker":{"url":"https://your-server/mcp/mcp","headers":{"Authorization":"Bearer <your-token>"}}}}. On the same machine you can run the server in stdio mode instead (python -m mcp_server from the backend directory) and it exposes the same tools over stdin/stdout.

  3. A read-only token cannot write — by construction

    Connect with a read-only token and the client lists 52 tools instead of 105: every mutating tool is removed from the tools/list response rather than merely flagged, so an agent that has never seen accounts_create cannot call it. If a client that cached the full list tries anyway, the server answers 403 with code mcp_read_only before anything leaves the process — no request reaches the app, no credential is issued. The demo tenant gets the same protection from the other side: its list is filtered the same way, each tool carries the title marker “demo tenant is read-only”, and its refusals come back with the app's own demo_account_restricted code.

  4. Every call leaves a receipt

    GET /api/v1/mcp-audit returns your own rows, newest first: which tool ran, the response code, how long it took, which token it came through, and a 64-character sha256 of the arguments. Arguments are hashed because a login call carries a password — the receipt answers “what did the agent touch?” without keeping the secret itself. Refusals are recorded too: a rejected write shows up with code 403, exactly like a successful one shows 200.

  5. Read what the agent did, then revoke it

    The trail is yours alone — it is scoped to your account the same way everything else is, and a different login sees none of your rows. Revoking the token kills access immediately (the next request comes back 401 with the body {"error":"Invalid MCP token"} — the machine-readable code invalid_mcp_token exists only on the internal validate endpoint, which the reverse proxy answers 403 to) while the rows it produced stay put: the log belongs to the account, not to the credential, so cleaning up tokens never erases the history you may want to check.

What one receipt tells you

FieldMeaning
toolThe MCP tool that was called — accounts_create, transactions_delete, and so on.
response_code200 for a success, 403 when the server refused it, the app's own status when the API rejected it, 500 for an unexpected failure.
duration_msWall-clock time of the whole call, measured at the MCP server.
mcp_token_idWhich token carried it — empty when the call arrived without one, as a local stdio session does.
args_hashsha256 of the arguments, so identical calls match and secrets never land in the table.
created_atWhen it happened.
